Radiata Stories — RMF Message Format

Reverse Engineering Reference — Claude assisted.
RMF1 is the container for every piece of displayable text in the game: field conversations, choice prompts, camp and menu strings, and save-slot names. This document describes the container, the 16-bit token stream inside it, and both of the opcode spaces that operate on that stream.

Facts are marked confirmed (read directly out of MIPS disassembly of the debug executable, or reproduced byte-for-byte against real packet data) or inferred (strongly implied by surrounding code or consistent across all observed data, but not independently proven).

The format is not identical across regions. Unless a passage says otherwise it describes both, and every difference found is called out where it belongs and summarised in §14.

Primary sources: the debug overlay step0_00.bin (base vaddr 0x001B4280) and the Japanese overlay of the same name (base vaddr 0x001A2380), plus their symbol maps and decompressed RMF payloads from both builds.

1. Where RMF data lives

An RMF payload always begins with the four-byte magic RMF1. On disc and inside the overlays it is normally held in a compressed container, so it must be decompressed before any of this applies; everything below describes the decompressed payload. The compression scheme is out of scope here.

Three families of engine code consume RMF payloads:

ConsumerEntry pointPurpose
CTalkCTalk::RmfStart(uint,uint,bool,bool,uint,uint)Full conversation playback: bustups, name plates, voice, choices.
CTalk (simple)CTalk::RmfStartSimple(uint,int,int,uint)Single-packet playback with no conversation state.
CSimpleMessageCCampObject::SetRmfMsg(CSimpleMessage*,uint,uint,uint)Camp and menu strings.
CRadiMemoryCardCRadiMemoryCard::GetSaveDataNameRMF()Save-slot display names, from a small RMF embedded in the overlay.

The Japanese copies are thirteen times larger than the English ones for the same 22 packets, because they carry a dynamic glyph payload that the English files do not (§13).

A debug-only overlay, RmfChecker.bin, drives CDebugRmfChecker — an in-game RMF browser. Its UI strings (file number, packet number, background number, character, mode, normal, simple, consecutive) name the arguments of RmfStart and are the source of the "file slot / packet number" terminology used below.

2. File header

The header is the one part of RMF that is region-dependent

The Japanese build places the packet offset table at 0x14; the English builds place it at 0x18. The English header carries one extra u32 that the Japanese header does not. Everything after the header — packets, tokens, commands — is identical (§14). A reader must therefore know the region before it can find the first packet.

All multi-byte values in RMF are little-endian. The header is a fixed block followed by a packet offset table.

A Japanese dialogue file, 6312 bytes with 16 packets, closes the case independently: [0x14] = 84 = 0x14 + 16*4 ✓ while [0x18] = 184 is not 0x18 + 16*4 = 88; and [0x08] + [0x0C] = 4608 + 1704 = 6312, the file size again to the byte, with 4608 / 512 = 9 whole glyph tiles.

In each case the word at the region's table offset is exactly the address one past the table, which is only true for the correct layout. The JP row also settles what [0x08] is: 9728 + 604 = 10332, the file size to the byte, so [0x08] measures the trailing payload and [0x0C] marks where it starts (§13).

3. Packet layout

A packet is one conversational block: a shared cast of speakers plus a sequence of messages. CTalk::RmfStartSimple positions the command stream like this confirmed: 

003104C4  lw    $a3, 0x00($v0)      ; glyph_budget
003104C8  lw    $a0, 0x04($v0)      ; speaker_count
003104D8  sll   $a0, $a0, 2         ; * 4 bytes per entry
003104DC  addu  $a0, $v0, $a0
          addiu $a1, $a0, 8         ; stream = packet + 8 + speaker_count*4
OffsetTypeFieldMeaning
0x00u32glyph_budgetTotal number of visible glyphs in the packet — the sum of every message's glyph count. Used to size sprite allocations up front.
0x04u32speaker_countNumber of entries in the speaker table.
0x08entry[n]speaker_table4 bytes each: u16 character_id, u16 variant_id.
0x08+4nu16[]streamThe token stream (§4).

3.1 The speaker table

Every command that names a character (0E 20 Speaker, 0E 24 Face, 0E 4E NameWindow, …) carries a 1-based index into this table, not a global character id. Index 0 means "no speaker". The indirection is what lets the same message stream be reused with a different cast.

The second u16 of each entry is 0 in ordinary field conversation packets. The engine passes the whole 32-bit word to CTalk::GetCharaNo (0x00315D10), which resolves it to a runtime bustup slot. Global character ids include pseudo-ids that resolve late — 9900 for the currently active character and 9901–9905 for the five party slots — so a packet can address "whoever is in slot 2" without the concrete id being known in advance.

3.2 Packet padding

In all observed data, packet bodies are padded to a 4-byte boundary and followed by a 4-byte 00 00 00 00 terminator, so packet offsets are always 4-byte aligned. The first 00 00 word of that terminator is a real token — command 0x00, dispatched to _CbEnd — and the remainder is slack. inferred

4. The token stream

The stream is a sequence of 16-bit little-endian words. There is exactly one rule for telling a glyph from a command, and it is decided by the low byte of the word (i.e. byte 0 of the record): 

b0 = stream[i+0]                    ; low byte of the word
b1 = stream[i+1]                    ; high byte of the word

if b0 >= 0x10:
    ; glyph: exactly 2 bytes
    size = 2
else:
    ; command record
    payload_words = (b1 >> 4) & 0x0F
    subcommand    =  b1 & 0x0F
    size          = 2 + payload_words * 2

This is not a heuristic. CTextMessage::WriteCommand(u16* dst, u8 cmd, u8 sub, u16 a, u16 b) at 0x002D4F50 is the engine's own record writer, and it ends with confirmed: 

002D5038  lbu   $a2, 1($a0)          ; current byte1
002D503C  andi  $v1, $a3, 0xf        ; payload_words & 0xF
002D5040  andi  $v0, $a3, 0xff
002D5044  sll   $a1, $v1, 4          ; payload_words << 4
002D5048  sll   $v0, $v0, 1          ; payload_words * 2
002D5050  addu  $v0, $a0, $v0
002D5054  addiu $v0, $v0, 2          ; return dst + 2 + payload*2
002D5058  and   $v1, $a2, 0xFFFFFF0F ; keep low nibble (subcommand)
002D505C  or    $v1, $v1, $a1        ; splice in payload count
002D5060  sb    $v1, 1($a0)

Two consequences are worth stating explicitly:

  • The words 0x0001 (space) and 0x000A (newline) are commands, not glyphs — command 0x01 and 0x0A with zero payload. WriteCommand accepts exactly 0x00, 0x01 and 0x0A as its zero-payload commands, which is the same set.
  • A decoder that consults a character table first, and only falls through to the record rule for unrecognised words, reaches the same answer — because no legitimate glyph has a low byte below 0x10.

4.1 Two opcode spaces, one stream

The stream is walked by CTextMessage::PutText(unsigned int slot) at 0x002D50E0. For every command record it does two things, in this order:

  1. Calls the owning object's TextCallBackCommand virtual (vtable slot +8) — for conversations that is CTalk::TextCallBackCommand at 0x00317EE0.
  2. Unless the callback vetoed it, runs its own handler from an 11-entry jump table at 0x003A3540, indexed by the command byte, valid only for 0x00–0x0A.

So commands 0x00–0x0A are presentation commands owned by the text renderer (§6), and commands 0x0E/0x0F are semantic commands owned by CTalk (§7). 0x06 is the one command that is meaningful to CTalk but has no renderer handler. Commands 0x0B–0x0D are inert in both spaces.

5. Glyph words

When PutText sees a word whose low byte is ≥ 0x10 it composes a 32-bit character code and hands it to TextCallBackCharacter (vtable slot +0xC) confirmed: 

002D5688  andi  $a0, $a1, 0xc0       ; b1 & 0xC0 -> attribute bits
002D5690  sll   $t2, $a0, 8          ;             ... to bits 14-15
002D5694  and   $a1, $a1, 0x3F       ; b1 & 0x3F -> font page
002D5698  addiu $s1, $s1, -0x10      ; b0 - 0x10 -> slot in page
002D569C  sll   $a0, $a1, 4          ; page * 16
002D56A0  lbu   $v1, 0xc($s4)        ; text style byte (cmd 0x05)
002D56A4  subu  $a1, $a0, $a1        ; page * 15
002D56AC  sll   $a1, $a1, 4          ; page * 240
002D56B0  addu  $s1, $s1, $a1        ; glyph index
002D56B4  sll   $v1, $v1, 0x10       ; style -> bits 16+
002D56B8  or    $v1, $v1, $t2
002D56C0  or    $s1, $s1, $v1

In other words:

glyph_index = (b0 - 0x10) + (b1 & 0x3F) * 240
char_code   = glyph_index | ((b1 & 0xC0) << 8) | (text_style << 16)

The Japanese build computes the same index from the same bytes, but packs two style bytes into the high half instead of one — _MES_DATA+0x0D at bits 16–23 and +0x0C at bits 24+, where the English build sends only +0x0C at bits 16+ and consults +0x0D separately. Nothing about the bytes in the stream changes, so this only matters if you are tracing the renderer. confirmed

FieldRangeMeaning

Example: 75 00 → b0 = 0x75, b1 = 0x00 → index 0x65 = 101 on page 0, which is the glyph 'S' in the English font.

Two separate decode tables are needed in practice: the English and Japanese fonts assign different characters to the same numeric word, so the region of a file must be known before its text can be read. A per-glyph advance-width table is also needed, for the layout maths in §11.

6. Layer A — text-engine commands (0x00–0x0A)

These are the eleven entries of the PutText jump table at 0x003A3540. All of them operate on the current _MES_DATA block; the offsets in the last column are fields of that structure. Everything in this section is confirmed from the jump-table handlers.

English builds advance the pen by (width * 12) >> 12, about three quarters of a cell; the Japanese build advances by the full cell, (width * 32) >> 12, and never computes the narrow term at all. Each bit selects one field of _MES_DATA to push or pop. This is a general-purpose style stack; ruby text (§12) is simply its most visible user.

7. Layer B — CTalk command dispatch (0x0E / 0x0F)

CTalk::TextCallBackCommand at 0x00317EE0 turns a record into a table index confirmed: 

00317EF4  lbu   $v1, 0($t0)          ; cmd[0]
00317EF8  bne   $v1, 0x0E, check_0F
00317F00  lbu   $v0, 1($t0)
00317F04  andi  $v0, $v0, 0xf        ; subcommand nibble
00317F08  addiu $v0, $v0, 0x10       ; 0x0E xN -> 0x10 + N
; check_0F:
00317F24  lbu   $v0, 1($t0)
00317F28  andi  $v0, $v0, 0xf
00317F2C  addiu $v0, $v0, 0x20       ; 0x0F xN -> 0x20 + N
; dispatch: index * 12 into ms_pCommandFuncTable
00317F3C  sll   $v0, $v1, 1
00317F44  addu  $v1, $v0, $v1        ; index * 3
00317F50  sll   $v1, $v1, 2          ; ... * 4  = index * 12
00317F4C  lui   $v0, 0x3b
00317F54  addiu $v0, $v0, 0x3a80     ; CTalk::ms_pCommandFuncTable
00317F5C  jal   0x149400             ; __ptmf_scall

Dispatch rules:

  • 0x00–0x0D: index is the command byte itself.
  • 0x0E: index is 0x10 + (cmd[1] & 0x0F).
  • 0x0F: index is 0x20 + (cmd[1] & 0x0F).

The runtime table CTalk::ms_pCommandFuncTable lives in BSS at 0x003B3A80, size 0x240 = 48 entries × 12 bytes (a Metrowerks pointer-to-member-function). It is populated from a static initializer at 0x0037EBD0 that uses 16-byte records shaped { u32 0, u32 0xFFFFFFFF, u32 callback_addr, u32 0 }, 48 of them. Both forms were dumped and agree. confirmed

0x250F 25_CbSentence2 words The wrapper that introduces a message. u16[2] = flags, u16[4] = glyph count. The sentence's own token stream starts at cmd+6 and runs to its terminator.
The callback calls SetSprtOutput(glyph_count, …) to reserve that many sprites, SetDefaultTextParam to reset style, then CTextMessage::TextOut(cmd+6, …) to render into a fresh slot, and returns 0x802 to retire the driver pass.
Flags: if flags & 3 is non-zero the callback first runs a measuring pass over the stream and back-patches the X field of every 04 20 record with -(line_width / 2) — the engine can auto-centre in place. In all observed field dialogue the flags are 0 and the coordinates are pre-computed instead.
0x260F 6x_CbPropersee note Proper-noun substitution. On first encounter it calls CTalk::SetProper(u16*, const RMFCOMMAND*) to expand a name into the scratch buffer at this+0xC8, appends a zero-payload 0F 6x terminator, saves the resume address in this+0xC4 and redirects the stream pointer into the buffer. The terminator hits the same callback, which restores the saved pointer. Returns 0x200 both times ("I moved the stream pointer myself").
Sizing exception: this is the one record whose length uses the whole second byte, not the high nibble — the payload is 2 * cmd[1] bytes.
0x270F 7x_CbJumpup to 7 words Reads u8[2] plus up to six more words at +4, +6, +8, +0xA, +0xC, +0xE.
Special role: CTalk::FirstCodeProcess(u16*) at 0x00310060 loops over leading 0F 7x records at the head of a packet and executes them before any rendering starts, returning the first non-0F 7x token. So Jump is effectively the packet prologue — scene setup that must run before the first sentence.
0x280F 28_CbPlaySe2 words u8[2] = channel, u16[4] = sound id.
If the channel byte is ≥ 0x10 it is treated as signed (slot -= 0x20). The value 0x1F therefore means -1 = "allocate a channel automatically", which additionally binds the playing handle to the current bustup so lip-sync follows the clip. 0x1F is what voiced dialogue uses throughout.
Suppressed entirely when the global sound-disable flag is set.
0x29–0x2F0F 9x–0F Fx_CbErr—Assertion trap. Seven unused subcommands.

8. Callback return flags

Every callback returns a value through this+0x1E0. PutText reads it as a bitfield — low byte is a state, high bits are directives. This is what makes constructs like _CbProper and _CbSentence possible. confirmed from the loop tail at 0x002D5CF8.

ValueNameEffect on PutText
low byte = 0continueKeep walking the stream (subject to the typewriter budget).
low byte = 1pauseStop for this frame; refund 0x100 of typewriter budget.
low byte = 2endFinish this text run. Clears the stream pointer.
0x100slot_goneDo not write the pen position back — the block is being freed.
0x200ptr_ownedThe callback already advanced the stream pointer; do not add (payload+1)*2.
0x400handledSkip the renderer's own jump-table handler for this record.
0x800releaseWith state 2: also free the sprite lists, the style block and the _MES_DATA itself.
0xFFerrorTriggers an assertion and aborts the run.

Observed combinations: _CbSentence returns 0x802, _CbProper returns 0x200, _CbEnd returns 2, and everything else returns 0.

9. Message archetypes

Three shapes account for essentially all real content.

9.1 Dialogue

0F 25 00 00 <glyph_count:u16>            Sentence header
0E 20 <speaker_idx> <00 00 | 01 00>       Speaker + bustup on/off
[02 20 R G B A]                            text colour   (default 6A 69 5F 80)
[02 21 R G B A]                            shadow colour
[03 20 <w:u16> <h:u16>]                   glyph cell, U8.8   (region-specific, §11.1)
[07 10 <speed:u16>]                       text speed, U8.8   (region-specific, §11.1)
[04 20 <x:s16> <y:s16>]                  line position
[0F 28 1F 00 <voice:u16>]                 voice clip
 0E 4E <idx> <mode> <offset> <name_id>    name plate
 <per-line 04 20 pos, 02 20 colour, glyphs, 0A 00 newlines>
 0F 20 <duration:u16> <03 00 | 02 00>    wait / continue cursor

9.2 Bare text

No 0F 25 wrapper and no speaker table use: the packet body is a bare token stream, distinguished by the absence of a Sentence header. This is the form consumed by CSimpleMessage, the camp menus, and GetSaveDataNameRMF.

9.3 Choice prompt

0F 25 00 00 <total_glyph_count:u16>
0E 20 <speaker_idx> <bustup>
[ … same optional style records as dialogue … ]
0E 4E <idx> <mode> <offset> <name_id>
0F 24 00 00 <choice_count:u16>            time limit 0 = none
<choice 0 tokens> 00 00
<choice 1 tokens> 00 00
…

The glyph count in the sentence header is the sum over all options, and each option is terminated by a bare 00 00 word (command 0x00, End). The name-plate offset is chosen from the option count using the same formula the line count drives for dialogue, so the plate clears the option list.

11. Layout mathematics

Text metrics are region-specific

The glyph cell, the text speed, the line spacing and the name-plate offset all take different values in Japanese files. These are authored data, not engine constants — the same 03 20 and 04 20 records carry them in both regions — but a reader that assumes the English numbers will mis-measure every Japanese line.

11.1 Glyph cell and text speed

Every dialogue message opens with a 03 20 dimensions record and a 07 1x speed record. Across a full English packet file and a full Japanese one, each is completely uniform within its region and differs between them confirmed:

Region03 20 payloadCell (U8.8)07 10 payloadSpeed
English33 0B 66 1611.20 × 22.4000 03 / 00 043.00, then 4.00
Japanese66 0E 00 1014.40 × 16.0000 077.00

The Japanese cell is wider and much shorter — nearly square, as full-width kana and kanji need — where the English cell is narrow and tall. Note also that the trailing 33 and 66 bytes in the English payload are just the fractional parts of 11.20 and 22.40; they are not fixed markers, and the Japanese payload uses 66 and 00.

The renderer derives its advances from that cell:

full_advance = (width  * 32) >> 12      ; one whole cell
line_height  = (height * 32) >> 12
space_narrow = (width  * 12) >> 12      ; English builds only
Regionfull_advanceline_heightSpace command 01 00 advances by
English22448
Japanese283228

That last column is a genuine engine difference rather than a data one, and it is visible in the jump-table handlers (§6): the English builds compute the extra * 12 >> 12 term and use it for the space command, so a space is about three quarters of a cell. The Japanese build never computes that term at all — its space handler advances by full_advance, so a space occupies one whole character cell, which is what Japanese typesetting expects. confirmed

11.2 Vertical placement

Line Y coordinates come from the 04 20 records, one per line, and the name-plate offset from u16[6] of the 0E 4E record. Observed values confirmed:

Lines English YEnglish plate Japanese YJapanese plate

2168, 20896168, 21688

Two differences fall out. Line spacing is 48 in Japanese and 40 in English, and the Japanese name plate sits at a fixed 88 for both line counts seen, where the English plate tracks the first line at first_y - 72. No three-line Japanese message appears in the sample examined, so the Japanese column stops at two.

The English series is a clean fit inferred:

n        = number_of_lines            ; 1, 2 or 3
first_y  = -5*n^2 - 7*n + 202
y(i)     = first_y + i * 40
plate_y  = first_y - 72

Two Japanese data points are not enough to fit a curve, so the observed values above should be used literally rather than extrapolated.

11.3 Horizontal centring

width_units = sum(advance_width[c] for c in visible_text)
rendered    = width_units * scale * 2/3          ; scale = 1.0 at the region's default cell
x           = -round(rendered / 2)

Each line carries its own 04 20 record, so a three-line box holds three independently centred X values. The alternative is to let the engine do it: setting flags & 3 in the 0F 25 header makes _CbSentence measure each line and overwrite these X fields itself (§7). Neither sample file uses that path — every 0F 25 in both carries flags = 0.

12. Ruby / furigana

There is no ruby opcode. Ruby is a composition built on the generic style stack (§6.1): save the style, shrink the glyphs, jump to an absolute position above the baseline, draw the annotation, then restore. The full sequence is: 

09 10 BC 00              StyleSave: pen X/Y, width, height, speed
03 20 33 04 66 0F        Dimensions -> 4.20 x 15.40  (vs 11.20 x 22.40 body)
04 20 <x> <y>            Position: centred over the base run, y - 28
02 20 6A 69 5F 80        Colour, matching the base text
07 10 00 00              TextSpeed 0 -> annotation appears instantly
<annotation glyphs>
09 11 BC 00              StyleRestore: same mask
<base text glyphs>

The annotation is emitted before the base text and positioned absolutely, so the base run's own advance is unaffected. Ruby X is base_center - annotation_width / 2, with the annotation measured at a scale of 4/11 to match its reduced cell width, and Y is line_y - 28.

Because the mask is a parameter, the same mechanism supports any scoped style change — a 09 10 with mask 0x03 would push only the colours, for instance. The BC 00 payload is specific to ruby, not a fixed constant of the format.

13. Embedded VRAM glyphs

Any bytes past packet_data_size (header +0x0C) are a raw 4-bit-per-pixel texture payload holding glyphs that are not in the base font — rare kanji that would otherwise not fit in the resident font pages. In practice this is a Japanese-only feature: header +0x08 gives the payload size and is 0 in every English file examined.

A payload measured end to end

The embedded Japanese SaveDataNameRmf decompresses to 10332 bytes with [0x0C] = 604 and [0x08] = 9728. Taking those 9728 bytes from offset 604 consumes the file exactly, with nothing left over, and 9728 / 512 = 19 — nineteen whole 32×32 tiles at 4 bits per pixel. The nibble histogram of that region is strongly bimodal at 0 and 15 with populated mid-tones, which is what antialiased glyph coverage looks like and is not what packet data or padding looks like. confirmed

… and the addressing confirmed against it

A Japanese dialogue file carries [0x08] = 4608 from [0x0C] = 1704, again summing to the file size exactly and again a whole number of tiles — 4608 / 512 = 9. Walking its token stream, every glyph word with the 0x80 attribute bit set falls in the range 0x8010–0x8017: eight distinct words, contiguous from the base, for a nine-tile payload. That is the tile addressing below, observed rather than assumed. confirmed

Decoding the payload inferred:

p0     = byte & 0x0F                  ; low nibble first
p1     = (byte >> 4) & 0x0F
pixel  = nibble * 17                  ; expand 4-bit to 8-bit grey
tiles  = reshape(pixels, (h, 32))     ; 32 x 32 tiles, stacked vertically

Tile i in the payload is addressed by the character word 0x8010 + i. Reading that back through §5: b1 = 0x80 sets the attribute bit and leaves the page at 0, and b0 = 0x10 + i is the slot. So the 0x8000 attribute bit is what marks a glyph as coming from the dynamic payload rather than the resident font.

The other attribute bit, 0x40, appears only in Japanese text and only rarely — four glyph words in the dialogue file examined, against 153 ordinary ones and 8 dynamic ones. Its purpose is still unknown (§15).

The Japanese executable was compared against the debug build function by function across the whole RMF path. The result is narrow: the container header differs, and the rest of the format does not. Verified identical between the two builds:

  • Packet layout. RmfStartSimple computes stream = packet + 8 + speaker_count * 4 from the same two header words in both.
  • Record size rule. WriteCommand splices payload_words << 4 into byte 1 and returns dst + 2 + payload*2 in both.
  • Dispatch. TextCallBackCommand uses the same 0x0E → 0x10+N / 0x0F → 0x20+N rules and the same index * 12 stride.
  • The 48-entry table. Dumped from both static initializers: the same callbacks in the same slots, the same _CbNop and _CbErr fill pattern, no additions or removals.
  • Every command's field offsets. _CbSentence (flags +2, glyph count +4, text at +6, the & 3 auto-centre test), _CbNameWindow (+2, +4, +6, +8), _CbJump (+2 and six words through +0xE), _CbPlaySe (including the ≥ 0x10 → slot - 0x20 sign trick), _CbWaitTime, _CbWaitSelect, _CbWaitSelect2, _CbSpeaker, _CbFace, _CbSignal, _CbProhibitSkip — all read the same bytes.
  • _CbProper. Same scratch buffer at +0xC8, same resume pointer at +0xC4, same whole-second-byte length exception, same 0x200 return.
  • The PutText jump table and all eleven handlers, including the 0x06/0x08 shared skip target, the colour word order, the U8.8 dimensions and speed, the % 3 text style, and the 09 mask semantics.
  • Callback return flags 0x100 / 0x200 / 0x400 / 0x800 and the 0xFF error path.
  • Glyph index maths. (b0 - 0x10) + (b1 & 0x3F) * 240, with b1 & 0xC0 to bits 14–15, in both.

Two build-flavour artefacts are worth knowing when reading addresses rather than the format: the Japanese executable is a retail build, so _CbErr collapses to a 0x10-byte stub instead of the debug build's 0x6C-byte assertion, and its resident glyph cache is walked with a different geometry. Neither changes a single byte of stream data.

14.1 How the Japanese addresses were recovered

The Japanese symbol map is a derived map whose confirmation policy omits any function whose body does not match the reference build, so PutText, WriteCommand, _CbSentence and the command table are all absent from it. They were located structurally instead: the 48-entry table by anchoring on _CbEnd, whose address the map does give, and searching backwards for the { 0, 0xFFFFFFFF, addr, 0 } record shape; the PutText jump table by its signature of eleven in-range targets in which entries 0x06 and 0x08 share a target; and function starts by walking back to the addiu $sp, $sp, -N prologue.

The method was validated by running it against the debug build, where it reproduced RmfStartSimple, RmfStart, RmfExit, PutText and GetCharaNo at exactly the addresses the full linker map lists, and against the English release, where every recovered callback matched the seven _Cb* rows its map does contain. Per-build addresses are in §16.

15. Open questions

  • The 0F 7x _CbJump payload words at +4 through +0xE are read but their individual meanings are not established. Given FirstCodeProcess, they are most likely background, camera and cast setup for the packet.
  • _CbBupDirection and _CbBupPosition are byte-identical stubs in the debug build; whether the retail build differs has not been checked.
  • The exact meaning of the three 05 text styles.
  • The 0x40 character attribute bit. It occurs only in Japanese text and only on a handful of glyphs — four distinct words in the dialogue file examined — which is too few to infer a purpose from context.
  • Whether Japanese three-line messages follow the English quadratic for line Y and plate offset. The sample examined contains only one- and two-line messages, and its plate offset is constant where the English one varies, so the English formula cannot simply be carried over.
  • Header +0x04 (0xCE) is present in every file, both regions, but no code that reads it has been found.
  • Header +0x08 is read as the VRAM payload size from file data alone; the engine code path that consumes it has not been located, so the naming is inferred rather than proven. Whether an English build would honour a non-zero value is untested.
  • Why the English header gained a total_size word at 0x14 when packet_data_size already carries the same value in every English file.
